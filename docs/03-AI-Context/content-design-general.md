# 内容设计通则(Content Design General Rules)

> **读者 = 设计 SoT 内容(天赋 / 技能 / 装备 / 遗物 / 职业)的 agent**(非人类工作者;人类设计文档见设计书面板)。本文放 `03-AI-Context/`,不进设计书面板、不同步 NAS。
>
> 本文承载**跨实体通用**的设计纪律;各实体专属要点见分册:[[talent-design-principles|天赋]] · [[skill-design-principles|技能]] · [[equipment-design-principles|装备]] · [[relic-design-principles|遗物]]。入口与真源清单见 [[design-rules-index|设计规则面索引]]。

---

## 1. 真源与查询次序(设计前必做)

- **规则真源 = 生产 `/api/rules`**（R1.x 战斗计算 / R2.x 人物系统 / R3.x 回合系统 / R4.x 棋盘系统）。`status=锁定` 的条目可作为现行规则依据；草稿不进入审计，也不作为参考材料。
- **tag 注册表 = `/api/tags`**：挂 tag 前读取 `definition` 与 `boundary`，确认语义和适用边界。
- **机制注册表 = `/api/resources`、`/api/states`、`/api/judgments`**：effect 涉及既有资源、状态或判定时，措辞与对应注册表定义对齐；`/api/terms` 仅作引用层，不保存机制事实。
- **职业 = `/api/classes`**：设计前确认职业存在、`tier`、`promotes_from`、`stat_tiers` 与 `weapon_types`；占位职业必须先由用户完成设计裁决。
- **实体现状 = `/api/talents`、`/api/skills`、`/api/equipment`、`/api/relics`**：设计前读取同池当前实体，核对名称、机制与直接字段。
- KB 的叙述性文档承载设计意图与展开解释；与规则或结构化事实冲突时，以设计库对应注册表和实体为准。
- 修改基座机制、术语或规则时，同批检查当前在库实体对它的引用，防止引用继续沿用失效依据。

## 2. 层定位先行(五层架构)

架构权威 = [[architecture-consensus-v2|五层架构共识 v2]](user-confirmed)。设计任何内容前先定它落哪层:

- **L2 天赋**(run 内完全清零)与 **L5 遗物**(6 格)= build-defining 层。
- **L4 装备**明确**不承担 build-defining**(硬约束):随机捡取 + run-reset,玩家无法围绕装备规划。
- **L1 Global** 只做横向解锁(更多选择),不做纵向变强。
- **纯数值裸属性强化归 L4 装备(词缀)/ L5 遗物(经济类)承载**;天赋(L2)承载机制 / 条件 / 构筑内容,不做裸数值件(用户 2026-07-19 裁决)。此条是「裸属性件归属」的判据本体,天赋册稀有度表按它执行、不另立标准;**规则表未收录此条**——R2.2 只讲成长与保底,不要去那里找数值形态纪律。幸运等 roguelite 轴属性件留作未来全职业池候选。
- 层错配是方向性错误——例如把流派改变型效果做进装备(那是 L5 的领地)。

## 3. 数值构成模式(三选,由定位决定)

**固定值**(前期 / 过渡件,后期被成长稀释)、**百分比乘区**(中后期构筑,追求分散乘区投资)、**属性挂钩成长型**(绑签名属性,强度重心在后期)三种模式没有唯一最优,由这件内容的**定位**决定,可单用或混合。权威锚 = 本节(数值形态分层,属设计裁决层、规则表未收录)/ R2.3(档位标尺,锁定规则)。可反复触发的概率类效果,后期期望次数按几何级数 `1 / (1 − p)` 增长,须设递减或上限——绑签名属性的概率件尤其容易踩。本节是这两条判据的本体,适用于一切带数值效果的实体;各模式的特性展开、可缩放属性触点表与天赋案例见 [[talent-design-principles|天赋册]] §1。

**乘区选择本身是定价决策**(2026-07-21 用户裁决):R1.8 的三种措辞(加算 / 提升 / 更多)不只是写法差异——它们把数值投进不同的乘区,而**同样的数字投进不同乘区,价值不同**。定标时先问「这个数值落进哪条乘区」,再问「给多少」。

- **判据 = 该乘区的拥挤度**。某条乘区已被频繁使用(库内多张卡都在往里加),说明它的边际效应已经严重:同样一点数值投进去会被既有堆叠稀释,实际收益低于投进一条使用较少的乘区。用户原话:「某个乘区已经被频繁使用了,说明该乘区边际效应比较严重。此时此乘区数值价值就会低于使用较少的乘区的数值。」
- **推论**:往拥挤乘区加数值,要给得更多才等价;往空乘区加,给少反而够。**「开一条新乘区」本身就是一种价值**,即使它的数字看起来不高——这也是本节「百分比乘区追求分散乘区投资」的理论依据。
- **不要为了整齐把两条通道统一成一种措辞**。数学不同的通道各自合法,应保留差异、在定标环节区别对待(2026-07-20 用户裁决:否决了「暴击伤害修正统一只用暴击倍率 +N」的提案)。
- 实例:暴击倍率可以同时存在**加算通道**(`crit_damage_bonus`,R1.3;如「暴击伤害 +N%」类词缀累加到基础倍率)与**独立乘区**(R1.8「更多」或明确写成倍率乘法;〔拔刀〕的独立暴击倍率修正属于这一类)。独立乘区单看倍率不高,但不吃加算通道的稀释,这正是它的定价依据。
- **拥挤度是定价输入,不是排他规则**(2026-07-22 用户裁决):多张卡可以、也应当共用同一条乘区——乘区总数有限,若一条乘区被一张卡用过就对其余卡关闭,可设计的天赋会迅速枯竭。拥挤只让边际收益变低,处理办法是在定价时计入(往热门乘区多给一点,或认下它值这个价),不是禁止再用。一张卡有毛病,先分清是「它的机制或数值有问题」还是「它真的选错了乘区」——前者远比后者常见;不要因为某条乘区热门,就判定把加成挂在这条乘区的卡本身错了。

**属性挂钩数值的预期基准**(2026-08-10 用户裁决):估算任何与属性挂钩的数值预期时,基准取**成长到 25 级的属性值 × 2**。属性不只来自自然成长,还有装备、遗物、技能与天赋的加成;只按 `base_stats` + 成长率推出的区间是**下限**,拿它当预期会严重低估实际强度。例:剑圣 DEX 自然成长区间约 9–25,预期按上限 25 × 2 = 50 估。反过来,测试里为了让断言有区分力而设的极端值(如 DEX = 100)不是生产数据,不能当证据。提请用户裁决时给出的数值区间须按此基准。

## 4. 措辞与修正代数(effect 文案硬约束)

效果文案必须使用 R1.8 规范措辞,保证机器可判定归层:

- **加算** =「X +N」;**提升** =「X 提升 N%」(同层加总后一次乘);**更多** =「N% 更多 X」(独立连乘);**无视 / 穿透** =「无视目标 N% X / N 点 X」(攻方效果,作用于对方量的消耗时点)。
- 层内顺序:加算 → 提升 → 更多;clamp / floor 是最外层守门;中间量不取整,最终量向下取整。
- 命中 / 暴击 / 伤害三链的每个公式量 = 独立乘区(R1.2 / R1.3 / R1.1)。写「暴击 +2」之前先确认它落哪一层。

展开解释见 [[01-Game-Design/Core-Systems/battle-calculation|战斗计算]](人类文档;与规则表冲突时以规则表为准)。

## 5. tag 与机制名合规

- 挂 tag 只从 `/api/tags` 现有注册表中选,严格按每条 tag 的 definition 与 boundary 判定,不凭直觉套语义(tag 分层维度已取消,现共 12 条,每条都有非空的 definition 与 boundary;boundary 现为写接口必填字段,用户 2026-07-20 裁决)。
- **职业特色资源不设专属 tag**:凡①让资源储备变多、②改写资源的规矩(上限 / 获得方式 / 兑换比例)、③依托资源当前数量做判定,三种关系之一的卡统一挂「资源」;技能自身标价的基础消耗不算(用户 2026-07-20 裁决,原话:「剑士/剑圣的技能除了斩击都消耗剑气,但这些和资源没有实质的直接联系。斩击可以获取剑气,所以可以关联资源」)。**剑气、印记**按此归并(印记 tag 已退役并入资源)。
- 不自造内部黑话 / 简写;需要新机制名时,先提请用户入对应注册表(资源进 `/api/resources`、状态进 `/api/states`、判定进 `/api/judgments`),再在 effect 中引用。

## 6. 文风(跨实体)

- **面向玩家的内容必须能直接进入游戏**：`name`、`effect`、`description`、`rules` 以及规则正文，均使用自然、完整、清楚的简体中文。禁止网络黑话、只在小圈子内流通的简称、翻译腔和机械化措辞；不得要求玩家先理解设计者或开发者的内部语境。
- **规则与规则说明同样属于玩家语料**：规则正文，以及技能或天赋中对规则的引用或解释，都必须在当前位置把玩家需要知道的内容说清楚。不得把规则编号、内部字段名、计算步骤或“参照某规则”当作正文，也不得用某个具体技能或天赋充当规则例子。
- **effect**：一两句，一遍读懂；不用箭头记号；复合名词有歧义时补“的”。
- **rules**：补充玩家需要知道、但不适合挤进主要效果文案的规则说明。它不是开发备注，仍须独立可读。
- **notes**：记录简短的设计意图或开发说明。这里可以保留必要的字段名、接口名和代码标识符，但正文仍应使用自然中文，且不得被卡面或规则说明直接引用。
- **结构化内容与文案分离**：触发时机、目标、条件、状态身份和数值参数由结构化字段保存；玩家文案负责解释结果。不得从文案反推执行关系，也不得把内部结构直接翻写成玩家文案。
- **速查纪律**：只陈述当前正面事实；禁日期、“原X”、否定式自辩、墓碑句和变更记录。作用域为设计库实体字段与规则表条文；`03-AI-Context/` 内部文档中用于追溯裁决出处的日期和署名不受此限。
- **规则表书写纪律**：每条只陈述当前正面事实；每条由 `group` 承载专属短标题；废止规则整条删除，保留编号空档且不重编号，并清理所有引用。修改后同步生产数据库、仓库快照与 KB 规则目录。
- 天赋和技能各有独立的 `rules` 字段，装备没有该字段，见 [[talent-design-principles|天赋册]] §5。

## 7. 命名

- **通用**:顺口、一眼可认、名字配合机制意象;借鉴对象 = 相关游戏 / 小说 / 漫画 / 动漫等**作品**中的典故(武侠、剑豪等题材经由这些作品取材,不做历史考据)。实体案例见各分册。
- **实体 id**:`<class_id>_<拼音slug>` 自动派生(pypinyin);装备 / 遗物前缀 `eq_wpn_` / `eq_arm_` / `relic_`(由 slot 驱动)。
- **职业线命名**(用户已裁决的可复用原则):每条职业线 = 1 下位 + 2 上位;class id 用英文全称(非拼音、非缩写)、贴该职业文化设定 / 原型、优先业界成熟职业名(火纹为主参考)。已建案例:myrmidon(剑士)→ kensei(剑圣)/ sword_immortal(剑仙)。**新职业线命名属重大决策,交用户。**

## 8. 状态与生命周期字段

- 新内容落库 `status=待审阅`；数值定稿前 effect 中的数值是草稿。
- 软删体系：`shelf_state`（已上架 / 已归档 / 待删除）+ `trashed_at`。只有「已上架」内容属于当前生效的设计材料。**新实体类型必须接入 `seed.import_payload`**（`POST /api/import` 的导入落库层，现役）——带软删状态的实体不接会在备份 / 导入时静默丢数据。
- 天赋 `levels_json` 是**设计层字段**：承载天赋升级型（lv2+）的分级草稿，由设计者手写，内层结构同天赋主体（effect / rarity / tags 等）。
- Agent 查询、过滤和写入枚举时，必须先读取 live API 或当前 schema 的真实值，不能把界面显示词当成尚未部署的字段值。跨仓术语迁移尚未部署完成时，回执必须明确记录 live 值与目标值的差异。
- 时间戳存 UTC；项目规范时区 = JST（UTC+9）。

## 9. 设计层 vs 引擎层(双轨字段,不可混谈)

| 维度 | 设计库(中文枚举,设计叙述用) | 引擎(英文,Godot 消费) |
|---|---|---|
| 伤害类型 | `damage_type`:无 / 物理 / 魔法 / 纯粹 / 混合(合法集 = 用户裁决) | 独立 taxonomy(Godot 仓权威;「圣」两侧都已退役,引擎侧收敛为 pure) |
| 行动资源 | `resource_type`:标准 / 迅捷 / 移动 / 反应 / 无 | `action_cost`:move / standard / swift / reaction / free |
| 技能定位 | `skill_type`:攻击 / 位移 / 增益 / 辅助 / 控制 | 无对应字段 |

双轨字段独立维护、描述同一现实;设计侧只写设计层字段,引擎层字段在 Godot 仓维护。两侧之间没有回填管线——`engine_json` / `eng_*` 只读镜像已随 2026-07-27 用户裁决退役,Ship 当前仍从自身的 Godot 数据文件读取可执行字段，尚未直接消费设计库 API；需要落地的设计层内容必须经过明确的跨仓实现。**不要把两套枚举当成同一个字段。**

## 10. 供给与审阅

- **供给上限管控已取消**：全部人工管理，审阅只提醒不阻塞；供给提醒交用户裁量，agent 不自行删除内容腾位。
- 审阅是提醒器，不是落库闸门；最终定稿由用户裁决。
- **日常审计对象仅为“待审阅”和“待优化”**，并且必须属于 `shelf_state=已上架` 的当前内容。
- **草稿、已归档和待删除既不进入审计，也不作为参考材料**；全量读取、备份或导出不会扩大审计范围。
- **锁定内容只作参考，不进入日常审计**；只有导入新规则改变其依据，或发现有具体证据的矛盾时，才按明确实体 ID 重新审计。
- 用户可以明确指定某个草稿作为修改对象；该授权只允许修改目标，不把草稿提升为审计样本或设计先例。

## 11. 裁决权边界(agent 不得自决,交用户)

- 新天赋从 0 到 1 的核心构想与候选方向由用户负责。agent 不从空白主动发明完整候选；收到用户构想后，负责事实核对、规则闭合、数值建模、结构整理、反方审查、文字优化、落库准备与方法论沉淀。
- 具体数值定稿(N 值 / 概率 / 属性系数)——agent 依据用户构想给出推演、验证与建议区间，最终取值交用户裁决。
- `damage_type` 合法集、rarity 档位体系等枚举的增删。
- 规则表条文的增删改(agent 可起草,落库前须用户确认)。
- 新职业线 / 新实体类型 / 新机制轴。
- 供给腾位、跨池搬移、整卡废弃。

## 12. 机制约定

- **机制绑定池纪律**：池内卡片必须以该池核心机制立足；通用轴的卡片放在通用层。移除池核心机制后仍然完整成立的卡片，不属于该机制池。
- **饱和维度检查**：设计前读取职业 `stat_tiers` 与相关判定链，确认目标维度仍有可感知的成长空间。
- **时点资源**：先攻优先级等时点资源按技能释放的一次性效果设计，不能写成条件维持型被动。
- **批量设计保持差异**：同时检查命名长度、trigger 形状、payload 类型、防滥用护栏、条件轴和节点形态；同一解决方式在一批内反复出现时必须改换设计轴。
- **条件必须在结算时点真实可变**：若前置机制已经保证条件成立，应按无条件效果定标。
- 天赋 `rules` 字段遵循天赋专属挂法纪律，包括避免防御性条款堆叠和逐字复述规则原文；详见 [[talent-design-principles|天赋册]] §5。
