# 视觉素材现行裁决

## 统一质感

- UI、人物、场景、地形与特效优先采用同一套视觉质感。
- 当前优先采用略微精细的像素或像素化插画方向。
- 战棋人物当前不以原生 48×48 像素画布作为前置门槛；优先使用与整体质感一致的精细透明源图，在 Godot 中按真实菱形格占位缩放，并检查相邻单位遮挡。只有这一路径在实际运行中无法兼顾可读性、遮挡关系和资源预算时，才允许战棋人物降低细节。
- 初版不要求战棋战斗动画。

## 人物与武器

- 人物原画与战棋人物之间保持身份、服装、配色和武器轮廓一致。
- 人物造型以用户确认的第三版统一质感代表板为当前参考，保持其中的脸型、发型、偏紧凑成年比例、服装剪裁、黑紫与旧金配色以及精细等距像素质感。
- 菱形格战棋人物采用相对屏幕正方向旋转 45° 的四个斜向，即朝屏幕左上、右上、左下、右下；不以屏幕正面、背面、左面、右面的正交四面作为默认方向。
- 武器外形允许采用传统中国剑、西洋剑或日式长太刀。
- 武器不得默认收敛为短刀、匕首或缺乏明确类别的狭窄刀形。
- 人物持剑时，手部必须清楚包握剑柄；不得出现武器浮空、脱手或仅靠身体重叠形成握持错觉。
- 剑圣人物素材必须分别提供单武器和双武器两套；每套都包含人物原画与完整四个斜向战棋人物，不在同一套方向稿中混用两种武器状态。
- 单武器套装的每张原画和方向稿都只显示一把武器；刀鞘或装备轮廓不得被误读成第二把武器。
- 双武器套装的每张原画和方向稿都明确显示两把武器；刀鞘或其他长物不得被误读成第三把武器。
- clean_v2 单武器与双武器四斜向精确文件的人物造型、武器状态、方向套装与格内 `frame_pivot` 定位均已通过用户视觉确认，是后续人物生成、清稿与原型集成的参考；正式战斗场景接入和生产素材准入分别验收。

## 素材来源与生成

- 购买任何素材前必须由用户确认。
- 一旦确认购买素材，后续本地生成链应向已购素材的质感靠拢。
- 当前生成优先使用 Codex 内置 GPT-Image-2，禁止改用外部 API key、SDK、命令行或 HTTP 调用。
- Rika 当前停用。
- 未经用户确认的生成候选仅供预览，不进入 Ship、设计库或 KB 的生产素材目录。
- 视觉确认只冻结造型与方向参考，不自动授权正式生产素材导入；正式导入仍需单独完成来源、许可、视觉与 Godot 可用性验收。

## 分类素材的共同准入规则

- UI、人物原画、战棋人物、地形与特效分别记录类型规则，不使用一组含糊的通用尺寸或导入参数覆盖所有素材。
- 每个候选必须记录素材类型、稳定标识、来源文件、源尺寸、预期显示尺寸、透明通道要求、纹理过滤方式和必需变体；不适用的字段应明确标为不适用，不得留给导入者猜测。
- 来源可追溯状态、使用权依据状态和用户批准状态必须分开记录：知道文件由何处产生，不等于已经核实可用范围；用户批准某个造型方向，也不等于批准后来生成或裁切出的具体文件。
- 新生成文件在用户逐个确认前只保存在仓库外的预览位置。只有具体文件获得用户批准，且来源可追溯与使用权依据都已明确核验为可导入后，才能进入 Ship 的原型素材目录。
- 当前 UI、人物原画、战棋人物、地形与特效五类代表预览的精确文件均已获得用户逐文件视觉批准；其精确身份由 Ship 清单记录的文件名、SHA256 与像素尺寸共同绑定。用户已明确授权这五个由 Codex 内置图像生成能力产生并经本地机械清理的精确文件用于 Ship of Theseus 项目、进行修改并随游戏分发，并授权将该声明作为本次原型导入的使用权依据；上述精确原文件可以进入原型准入流程。该授权只覆盖由清单绑定的五个精确文件。后续裁切、重编码、清理或其他衍生字节不自动继承这些精确文件的视觉批准，必须重新确认或建立明确的衍生审批记录。
- clean_v2 战棋人物衍生文件已另获用户逐文件视觉批准，并完成隔离 Godot 的加载、切帧和多分辨率运行检查；其人物主体 `frame_pivot` 定位也已获得用户最终视觉通过，不再阻塞后续原型集成。使用权依据来自前述修改授权，精确身份与原型状态由 Ship 清单记录；这些结果不自动授予正式战斗场景或生产素材准入。
- 原型目录准入不等于生产素材准入。转为生产素材前仍须完成来源、使用权、视觉一致性、Godot 导入和运行表现验收；购买或接受外部许可始终需要用户单独确认。
- 同一人物、建筑或效果跨类型出现时，应保持身份特征、轮廓语言、主配色、像素密度和光照方向一致；为适配尺寸可以删减细节，不得改成另一套质感。

## UI 素材规则

- 回合制技能冷却统一显示整数形式的剩余回合数：冷却大于 0 时，在技能槽中央显示数字，并以半透明近黑暗层压低亮度但保留图标辨识度；冷却归零时隐藏数字与暗层。不得用比例色块、进度条或烘焙冷却图片表达冷却。
- 可复用 UI 图片只承担中性表面材质。快捷键、冷却数字与暗层、次数、选择、悬停、按下、禁用、足迹、移动数值、行动点和资源消耗状态必须由 Godot Theme、控件或运行时覆盖层表达，不得烘焙进中性外壳图片。
- 同一技能槽的常态、悬停、按下和禁用状态共用一张中性表面，通过 Theme 调色和独立覆盖层区分；不得为每个状态复制一张生成图片。被动技能即使具有主动效果，也沿用同一槽位和快捷键职责，不以图片类别标记区分。
- 行动资源条图片只承担外部细框，内部三个语义区域、实际容量 1—3 的标准行动圆点与迅捷行动三角、向上足迹及移动数值均保持为独立运行时组件。图片不得包含资源点、分隔柱、文字或数值。
- 小尺寸 HUD 外壳采用“高分辨率生成母版—透明通道核验—机械清理—目标尺寸派生—Godot 九宫格接入—三档截图”的流程。若生成结果把透明棋盘烘焙进 RGB，必须保留原始结果，只允许按高亮低色差灰白背景机械生成透明度；外部和中心透明度需分别用自动断言核验。
- 技能槽目标派生尺寸为 64×64，并须在 58×58 内部布局中复用而不改变技能栏外框；行动资源条目标派生尺寸为 274×40。两类表面均须验证边角闭合、长边无接缝、内容区不受污染，并保留 1 像素级透明安全边以防缩放滤波污染画布角点。
- 角色栏固定结构以 226×108 外框、72×82 头像窗口和 124 像素信息列为当前基线；名称、等级／经验、HP／护盾三组高度依次为 18／20／28，组间距均为 8。说明文字不参与几何计算。
- 角色名称行采用“职业名 · 玩家自定义名称”。名称单行截断时必须保留完整 tooltip；等级、经验、HP、护盾及其 `当前值/最大值` 文字均由运行时 Label 与有类型显示数据产生，不得烘焙进图片。
- HP 与护盾位于一个共同外框内，但保留两条独立的填充和数值。经验、HP、护盾的比例由 ProgressBar 运行时表达；轨道背景、填充、数值字体与描边继续由 Theme 控制，不生成固定比例图片。
- 角色栏的下一最小图片职责只包含 226×108 角色栏中性外壳和 72×82 头像框中性外壳；头像内容、fallback 字符、字段文字、轨道和填充均不进入外壳图片。两项外壳沿用同族暗黑哥特细像素材质与透明机械清理流程。

## 人物原画规则

- 当前人物原画沿用第三版统一质感代表板中的脸型、发型、偏紧凑成年比例、服装剪裁、黑紫与旧金配色及精细等距像素化插画质感。
- 单武器和双武器必须是两套独立变体；单武器仅一把剑，双武器恰好两把剑，武器形状、实际握持和多余长物限制沿用“人物与武器”章节。
- 原画源尺寸和预期显示尺寸分别记录，不把屏幕显示尺寸反推为固定源文件尺寸；缩放后必须保留面部、发型、服装和武器类别的可辨识度。
- 人物主体与武器需要透明背景，展示用底板或排版文字不得合并进可导入原画。
- 人物原画属于略微精细的像素化插画，不以 48×48 战棋人物的像素密度直接放大，也不改成与战棋人物无关的平滑厚涂风格。

## 战棋人物规则

- 当前采用高分辨率透明源图，在 Godot 中按真实 64×32 菱形格占位缩放验证；不再要求先把代表样本重制为原生 48×48 像素画布。
- 每套包含屏幕左上、右上、左下、右下四个斜向，方向标识固定为 NW、NE、SW、SE；不得使用正面、背面、左面、右面的正交四向替代。
- 单武器和双武器分别形成完整四向套装。单武器每帧恰好一把剑；双武器每帧恰好两把剑且分别由两手握持。
- 文件使用透明背景。当前已批准的精细人物默认使用 Linear 过滤，Nearest 保留为诊断对照；源图尺寸、切帧区域、方向顺序、变体、逐帧 `frame_pivot` 和显示缩放由 Ship 清单记录。
- 格内定位必须使用逐帧显式 pivot：横向以头部—胸腔—骨盆形成的人体解剖中轴为准，并排除武器、刀鞘、武器附件和外飘披风；纵向取双脚接地点的中点。
- 不得用整帧透明包围盒、整体 alpha 质心、武器轮廓、最低单脚或统一帧中心自动推断人物 pivot。自动测量只能提供候选，必须通过真实菱形格中的人物主体视觉审核。
- 在真实 Godot 格子、相邻单位遮挡和目标分辨率下，必须能辨认人物身份主特征、朝向、武器数量和落脚位置；只有该运行验证无法兼顾可读性、遮挡关系与资源预算时，才允许降低战棋人物细节。

## 地形素材规则

- 基础地块采用 64×32、宽高比 2:1 的菱形画布，与当前菱形战棋格一致；菱形外区域保留透明通道。
- 可连续地面必须验证相邻连接和重复铺设，避免边缘断裂、亮度接缝或每格都出现强烈独立边框。
- 地面基底与树木、建筑、遗迹、悬崖等遮挡物拆分；覆盖物使用透明背景，不把人物、功能图标或玩法提示烘焙进地形。
- 地形使用 nearest 过滤，并与人物和 UI 保持相近的像素密度、黑紫与旧金色彩关系及统一光照方向。
- 当前代表样本只冻结地块规格、连接方式和质感，不据此补充移动消耗、阻挡或其他玩法规则。

## 特效素材规则

- 当前分类包括斩击、移动路径、范围指示和状态提示，全部使用透明背景，并保持与人物、UI 相同的主配色、像素密度和克制的发光范围。
- 斩击特效的形状应强化剑类武器的长弧或锋线，不得把武器类别改读为短刀；范围与状态特效不得遮住人物朝向和武器数量。
- 静态关键帧、图集帧尺寸、播放顺序和预期显示尺寸分别记录；不同用途的特效不得因共用一张展示板而失去独立导入能力。
- 初版特效以静态关键帧或参考板验证质感与可读性，不要求完整循环、粒子系统或战斗动画。
- 像素轮廓默认使用 nearest 过滤；确需柔和衰减的独立光晕层可以使用 linear，但必须与像素核心层拆开并在清单中声明。

## Godot 验证

- 若出现 Godot 版本问题，先升级到合适的维护版本，再执行 Playground 和回归验证。
- 具体文件进入原型目录后，按素材类型核验尺寸、透明通道、过滤、变体完整性、方向顺序和独立导入，并在 720p、1080p、1440p 三档显示下检查质感与可读性。
- clean_v2 当前隔离 Playground 覆盖三档分辨率、Nearest 与 Linear 同帧对照、连续 7×5 菱形格相邻遮挡、单双武器四斜向和人物主体定位；逐帧 `frame_pivot` 人体中轴版本已获得用户最终视觉通过，不再阻塞后续原型集成。
- 隔离 Playground 的验证结果不等于正式 TacticalScene、Unit 或生产资源管线已经接入。

## 专用工具与质量门槛

- 视觉素材、HUD 布局、动效与其他具有成熟专业流程的设计场景，允许主动引入更适合该任务的新工具、文件格式或本地工具链；不得因为当前会话已有通用工具，就降低到通用代码画布或临时拼图能够达到的标准。
- 工具选择必须先核对任务类型、可编辑模型、组件与图层能力、网格与约束能力、导入导出、版本留存、Godot 衔接、许可与安全边界。引入工具的授权不替代素材购买确认，也不授权使用外部 API key、付费账户、外部凭据或未核实许可。
- 正式设计产物必须保存可继续编辑的源文件，并保留组件边界、图层命名、尺寸、间距、锚点、约束和目标分辨率。截图与渲染图只用于审核，不得取代可编辑设计源。
- HTML、脚本生成画布和类似通用技术可以承担交互验证、分辨率回归、重叠检测或临时诊断；除非经核对确实符合该专业场景的生产标准，否则不得作为正式视觉设计源。
- 提交用户审核前，必须按对应领域的一般专业方法检查信息层级、组件职责、布局约束、视觉一致性、可编辑性、可实现性和多分辨率表现，并安排独立审查。仅能显示、没有越界或通过脚本检查，不等于达到设计质量门槛。
- 发现既有工具或方法使产出质量明显偏弱时，应回到工具选择和工作方法重新评估，必要时更换专用工具并重做当前阶段，不在较弱基础上继续堆叠后续产物。
- 当前 HUD 组件布局以 Penpot 作为正式设计工具：Penpot 保存正式可编辑布局源，HTML 只保留为机械验证器；用户确认各职责组件的相对位置与尺寸后，再设计内部样式，最后进入 Godot 的 Control、锚点和 Container 映射验证。
- Agent 自动化使用用户已登录的外部 Chrome 打开 Penpot，并由 Penpot MCP 插件连接本机服务；Codex 内置浏览器不共享外部 Chrome 的登录状态，不作为该流程的登录入口。流程不得索取或使用外部 API key。
- Penpot 应用与本地 MCP 插件使用一致的完整版本号。当前已验证的组合为 Penpot 2.17.2 与 MCP 2.17.2；升级任一端后必须重新执行真实文件冒烟测试，不以“无版本警告”单独作为通过依据。
- 正式设计开始前的冒烟测试至少覆盖：读取当前页、在隔离画板中创建和修改对象、Flex/Grid 布局、组件主实例与复制实例、局部设计变量，以及 PNG/SVG 导出和文件格式回读。隔离测试画板不得混入正式 HUD 组件。
- 当前 2.17.2 本地服务的 SVG 文件导出需要把插件返回的 Base64 字节封装按 UTF-8 解码；本机运行时已加入该兼容修正。以后升级 MCP 时必须先复测原生 SVG 导出，确认上游已修复后再移除本地修正。
