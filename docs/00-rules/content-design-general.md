# 内容设计通用指引(Content Design Guide)

> **读者 = 设计 SoT 内容（天赋、技能、装备、遗物、职业）的代理。** 本文是三级指引：解释 [设计规则总表](rules.md) 中跨实体的规则，给方法与示例，不另立规则；与总表不一致时以总表为准。入口见 [设计规则面索引](design-rules-index.md)。

## 1. 五层定位怎么判断

架构权威是 [五层架构共识 v2](../03-decisions/architecture-consensus-v2.md)；规则见 G09、E01、L01、T01。

- **L2 天赋**（局内完全清零）与 **L5 遗物**（6 格）定义构筑；**L4 装备**随机捡取、局后清零，玩家无法围绕它规划，所以不承担构筑定义；**L1 全局**只开放更多选择。
- 判断方法：问「玩家会不会为了这件东西改变打法或加点方向」。会，就属于 L2 或 L5；只让同一打法更强一点，属于装备或经济类遗物。
- 典型错配：把改变流派的效果做进装备（那是遗物的领地）；把纯裸属性加成做成天赋（T01，裸属性归装备词缀与经济类遗物）。

## 2. 数值模式与乘区

规则见 N01–N06。

**三种数值模式的取舍**（N01）：

| 模式 | 例子 | 特性 | 适合 |
|---|---|---|---|
| 固定值 | 暴击 +10 | 前期占比高，后期被成长稀释 | 前期、过渡件、低稀有度节奏件 |
| 百分比乘区 | 伤害提升 N% | 效果取决于所在乘区；多个独立乘区各投一点，相乘后优于单乘区堆叠 | 中后期、乘区互补的构筑 |
| 属性挂钩 | 暴击 + 技巧/2 | 前期明显偏弱，随属性成长走强；强度重心在后期 | 成长型件、绑定职业签名属性 |

固定值不是「低级」，属性挂钩也不是「高级」，各有适用区间。先定这张卡的定位，再选模式。属性挂钩的件前期弱是设计代价，定标时确认后期给足补偿且不失控。

**概率效果为什么要设上限**（N02）：可反复触发、每次成功率为 p 的效果，期望触发次数按 `1 / (1 − p)` 增长；p 绑签名属性时，后期会被推到失控区间。递减（例如每成功一次概率乘 0.8）或频次限流至少用一种。

**乘区拥挤度怎么用**（N04、N05）：某条乘区已被库内多张卡往里加，同样一点数值投进去会被既有堆叠稀释。所以往拥挤乘区加要给得更多才等价，开一条使用较少的乘区本身就有价值。拥挤只影响定价，不是禁令：一张卡有问题，先分清是机制或数值有问题，还是真的选错了乘区，前者常见得多。

**属性挂钩数值的预期基准**（N06）：属性不只来自自然成长，还有装备、遗物、技能与天赋加成，只按基础值加成长率推出的区间是下限。例：剑圣技巧自然成长区间约 9–25，预期按 25 × 2 = 50 估。

**修正怎么归层**：写法与归层见设计库 R1.8，伤害各层见 R1.1；展开说明见 [战斗计算](../01-Game-Design/Core-Systems/battle-calculation.md)（与规则表冲突时以规则表为准）。暴击倍率可以同时有加算通道（「暴击伤害 +N%」累加到基础倍率）与独立乘区（明确写成倍率乘法），两者数学不同，按 N04 各自保留。

## 3. 字段职责示例

规则见 W05–W09。

| 字段 | 写什么 | 写法示意（不是在库卡片） |
|---|---|---|
| `effect` | 效果本身，一两句读懂 | 「对目标造成物理伤害，并使其处于〔某状态〕状态。」 |
| `rules` | 本卡特有、玩家需要知道但塞不进 `effect` 的结算细节，用平实的话写 | 「同一次使用命中多个目标时，只获得一次剑气。」 |
| `notes` | 设计意图与开发说明，可以含字段名 | 「剑气循环里的低稀有度节奏件。」 |

不要在 `rules` 里写「见 R1.10」或复述规则表已有的默认口径；规则表管所有卡共同的结算，卡面只写本卡不同于默认的部分。卡面也不写本卡与其他天赋、技能的交互顺序（W02）：例如不写「在〔阴阳调和〕等效果额外失去的剑气计入之前扣除」，这类先后由规则表统一规定。

## 4. 设计层与引擎层（双轨字段）

规则见 G10。设计库与 Godot 引擎各有一套字段，描述同一现实、各自维护，中间没有自动回填：

| 维度 | 设计库（中文枚举） | 引擎（英文，Godot 消费） |
|---|---|---|
| 伤害类型 | `damage_type`：无、物理、魔法、纯粹、混合 | 引擎自己的伤害类型 |
| 行动资源 | `resource_type`：标准、迅捷、移动、反应、无 | `action_cost`：standard、swift、move、reaction、free |
| 技能定位 | `skill_type`：攻击、位移、增益、辅助、控制 | 无对应字段 |

Ship 当前从自身的 Godot 数据文件读取可执行字段，不直接消费设计库接口。设计库里写好的内容要落地，必须另做一次明确的跨仓实现。不要把两套枚举当成同一个字段。

## 5. 审计范围与生命周期

规则见 G02–G04、P08。

- 设计库记录有两组状态：`shelf_state`（已上架、已归档、待删除）管它还在不在用；`status`（草稿、待审阅、待优化、锁定等）管它的设计成熟度。先按 `shelf_state` 再按 `status` 筛选。
- 日常审计只看已上架的待审阅与待优化记录；锁定记录只作参考。
- 天赋的 `levels_json` 是设计层字段，承载天赋升级型（lv2 以上）的分级草稿，内层结构同天赋主体。
- 时间戳存 UTC；项目规范时区是 JST（UTC+9）。
- 实体 id 由设计库按 `<class_id>_<拼音>` 自动派生，装备与遗物的前缀由 `slot` 决定。

## 6. 批量设计的分布检查

规则见 P12。同时设计一批内容时，逐项看分布：命名长度、trigger 形状、效果类型、防滥用护栏（频次、递减、条件）、条件轴、节点形态。某种解决方式在一批里反复出现，就换一条设计轴，而不是换个名字重复。
