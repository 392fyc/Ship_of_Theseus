# Spec Kit 外层采用方案

**状态：** 技术验证通过，按最小本地 workflow 方案采用

**目标：** 用 Spec Kit 承担可替换的项目级外层流程，同时把三库权威、Mercury 裁决、仓库安全规则和具体领域流程留在各自现有位置。外层只负责把一次工作从“收到需求”带到“完成验收”，不复制业务数据，也不建立第二套权威。

## 一、采用结论

采用“一个工具安装、一个项目集成、三库不重复部署”的形式。

- Spec Kit CLI 固定为 `specify-cli==1.0.1`，只安装在 Windows 当前用户的 `uv tool` 环境。
- Spec Kit 项目集成只放在默认 Codex 工作根 `Ship_of_Theseus`，版本化源文件为 `.codex/project/workflows/sot-outer.yml`，运行状态放在被忽略的 `.specify/workflows/runs/`。
- 设计库和 KB 不运行 `specify init`，不生成自己的 `.specify`、Spec Kit skills 或 workflow 副本。
- 正式启用前先用 `uvx --from specify-cli==1.0.1 specify` 做临时验证，避免验证阶段污染用户级工具环境。
- 正式项目也不提交默认 `specify init` 生成的完整 SDD workflow、模板和 10 个 `speckit-*` skills；SoT workflow 通过本地 YAML 路径运行。
- Spec Kit 是可切除的控制层，不是第四个业务仓库，也不接管三库权威。

选择 `Ship_of_Theseus` 作为唯一项目集成位置，是因为它已是 SoT 日常开发的默认 Codex 工作根，现有 `AGENTS.md`、`.codex/` 和 `.agents/skills/` 都从这里进入。这个选择只表示“流程入口位于此处”，不表示引擎仓取得设计库或 KB 的业务权威。

## 二、各层边界

### Spec Kit

只负责：

- 保存外层 workflow 定义、运行状态和可恢复步骤；
- 收集一次任务所需的最少输入；
- 调用 Mercury 进行权威路由、任务拆分和风险判断；
- 调用相应领域 skill 或具体小框架；
- 在结束时要求一次独立核对和任务回执。

不得负责：

- 保存或修改天赋、技能、State、叙事、玩法规则等业务事实；
- 自行决定跨仓权威归属；
- 代替 Git/GitHub 记录提交、任务范围和验收证据；
- 在外层 workflow 内复制设计库、KB 或引擎数据；
- 通过无限循环反复修复、复审或扩大测试范围。

### Mercury

Mercury 继续负责项目级判断：

- 根据用户需求确定目标仓和唯一权威；
- 判断任务规模、是否拆分、是否需要子代理；
- 给子代理下发明确目标、写入范围、停止条件和验证范围；
- 处理跨仓顺序、用户裁决和未决风险；
- 在发现任务超出原规模时中止当前任务，而不是自动扩张。

Spec Kit 只记录路由选择和人工确认点，不直接调用 Codex 子代理。Mercury 继续使用 Codex 原生协作能力执行分发，不重写这些判断规则。

### `AGENTS.md`

`AGENTS.md` 只保存长期稳定且进入仓库后始终生效的规则：

- 权威路由；
- 安全与秘密处理；
- 分支、worktree 和提交限制；
- 语言与代码约定；
- 跨仓写入前置条件。

不把具体 workflow 步骤、任务字段矩阵、审查记录格式或模型预算表塞入 `AGENTS.md`。这些内容变化较快，应该留在 Spec Kit workflow、Mercury 合同或具体小框架中。

### Skills 与具体小框架

Skills 保存领域操作知识，例如设计库安全读写、KB 写入、会话开始和任务回执。Spec Kit 只按名称调用，不复制其正文。

高耦合的小框架只用于明确、重复、边界稳定的具体工作，例如：

- 天赋设计与数值推演；
- 人物或场景素材生产；
- State 数据编辑与导入检查；
- 某类 UI 视觉验收。

小框架可以有更严格的字段、模板和验证，但不得把这些要求反向提升为所有任务都必须遵守的外层规则。

## 三、最小外层 workflow

外层只保留四个阶段，不建立自动修复循环。

1. **接收**：记录目标、预期交付物、可能涉及的仓库和用户明确的限制。
2. **路由**：由 Mercury 确定唯一权威、任务规模、写入范围、是否需要具体 skill 或小框架。
3. **执行**：把一个有边界的任务交给主代理或一个实现子代理。默认不允许子代理继续派生；确需派生时必须由任务本身说明。
4. **核对与结束**：根据变化风险运行聚焦验证，安排一次独立核对，生成回执。核对发现超出原目标的新问题时记录为后续任务，不自动扩大当前任务。

外层 workflow 不强制每次都走完整的 Spec Kit `specify → plan → tasks → implement` 链。简单任务允许从接收直接进入执行；只有需要正式规格或多人分工的任务才启用相应阶段。

## 四、任务规模与子代理约束

外层只做粗粒度分级，具体数值可以根据以后模型变化调整。

- **S：** 单一交付物、少量文件、无跨仓写入。主代理直接完成，通常不派实现子代理；需要独立核对时只派一个只读核对者。
- **M：** 单仓多文件或一个清楚的跨层变化。最多一个实现子代理和一个独立核对者；必须预先写清停止条件。
- **L：** 跨仓、高风险迁移或多个可独立交付物。必须先拆分为若干 S/M 任务；只有无法合理拆分的部分才交给更高能力或更高预算的子代理。

主会话永远不设置 token 预算。子代理预算只是停止和升级信号：预算不足说明任务估级错误或拆分不足，不允许以“继续补测试”为理由无限提高预算。每个子代理还必须收到以下约束：

- 一个主要交付物；
- 明确允许写入的文件或目录；
- 明确不处理的相邻问题；
- 最多一次汇总式修正；
- 不自行扩大测试矩阵；
- 发现任务规模明显偏离估计时停止并回报。

## 五、验证强度

外层不再维护复杂的全局测试复用指纹、验收项路径×用例矩阵或多轮审查状态机。

- 文档和控制文件变化：运行格式、解析、引用和最小流程验证。
- 单仓代码变化：运行聚焦测试及直接受影响测试。
- 跨仓写入、数据库迁移、发布或公共接口变化：由对应小框架决定是否需要完整回归。
- 独立核对只检查用户目标、允许范围、明显回归和证据是否足够；普通改进建议不得阻塞当前任务。

## 六、切除测试

正式启用前必须证明 Spec Kit 可以完整移除而不破坏三库日常工作。

切除测试按以下顺序进行：

1. 在临时项目中安装本地 workflow，完成一次无业务数据的运行与恢复。
2. 移除该 workflow，并确认它贡献的文件和运行记录可识别、可删除。
3. 删除临时项目中的 `.specify` 与验证时由默认初始化生成的 `speckit-*` skills；正式项目不引入这些生成 skills。
4. 确认原有 `AGENTS.md`、`.codex/agents` 和 `sot-*` skills 没有被修改或删除。
5. 确认 Ship、设计库、KB 的业务文件均未发生变化。
6. 确认不用 Spec Kit 时，Codex 仍能从 `Ship_of_Theseus` 根目录读取 `AGENTS.md`，并按原有 Mercury 与 skills 流程工作。

正式方案必须允许只删除以下两类内容完成切除：

- 用户级 `uv tool` 中的 `specify-cli`；
- `Ship_of_Theseus` 内的 `.codex/project/workflows/sot-outer.yml` 和被忽略的 `.specify/workflows/runs/`。

如果切除还要求修改设计库、KB、玩法代码或长期安全规则，则本方案判定失败。

## 七、已知限制

- Spec Kit workflow 的 `requires` 只是声明，不是安全沙箱；workflow 仍必须由项目规则限制写入范围。
- shell 步骤的字符串替换不能接收未经限制的用户文本。本项目外层 workflow 不把自由文本直接插入 shell 命令。
- 当前 Codex 扩展命令存在上游兼容问题，因此技术验证不安装社区扩展，也不依赖扩展之间的命令跳转。
- Spec Kit 的 workflow 和 bundle 只用于组合与分发，不视为业务权威或安全边界。

## 八、采用门槛

只有技术验证同时满足以下条件，才进入正式落地：

- 固定版本可安装并报告正确版本；
- Codex 集成文件位置可预测；
- 本地 workflow 可校验、安装、运行、暂停或恢复；
- 运行过程不写三库业务数据；
- workflow 可移除，临时项目可完全清理；
- 现有 SoT skills 与 `AGENTS.md` 不受影响；
- 根据验证结果能够删除而不是增加旧 harness 的复杂机制。
