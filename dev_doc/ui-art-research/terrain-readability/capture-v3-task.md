# 地形同帧采集 v3：动态高亮状态归一化

## 阶段成果与完成条件

本项继续完成 TERRAIN-READABILITY-01 的同帧基线采集前置。先证明采集工具能取得真实、对齐且可测量的原件，再测当前素材并校准负例。地形问题、基础战斗 UI 和 P0/CR-01 Milestone 仍未完成。

本项完成条件：小范围修正测试工具；以真实正式会话复现单侧输入造成的状态差异并验证归一化；独立源码审查后冻结完整提交；通过 dot-link 投递新任务，由 Dot 取得原生像素证据；本地完整消费原件、重新运行现行检查、独立审查并发送签名回执。源码或无窗口结构通过不能代替像素验收。没有发布授权，不推送、不建 PR。

## 重新评估与修正依据

冻结 v1 候选 `d4d53d1934e631ccc17940a1b19d1a68561ec722` 的六组实际采集不能建立可测量基线；两组 720p 的主图与独立重建图不同，排除掩膜全白，四个高档没有原图。冻结 v2 候选 `1be74a111c13ad558c089b3a8bcd4be04b406220` 的 TASK46 六组均在动态高亮节点匹配处退出，没有 PNG、清单、当帧诊断或实际纹理尺寸。两轮没有像素前置进展，按项目约定重新评估实现方式。

独立只读诊断支持以下因果链：主会话在根 Viewport，重建会话在独立 SubViewport；v2 只向根 Viewport 发送场外鼠标事件。两套 TacticalManager 可以保留不同的悬停高亮，而 BoardView 的无悬停可见性上下文不改变管理器状态。高亮节点按状态清除并重新创建，自动名称与节点总数不能作为稳定匹配依据。TASK46 原日志没有记录双方当时的悬停标志及高亮数量，不能把具体失败 Polygon2D 推断为已证实的悬停覆盖。

采用更小的修正：在测试工具内归一化两个实际管理器的悬停状态；保留各自独立生成的高亮，严格比较其绘制数据，不再按自动节点名查找动态高亮。完整 RGBA 等价门禁继续保留。

## 必需检查

1. 在真实正式会话中，仅向根 Viewport 发送场外鼠标移动，检查主、重建管理器实际出现的状态差异；然后使用既有正式接口将相同场外状态应用到双方，等待延后删除完成，验证双方均无悬停。
2. 比较双方独立生成高亮的顺序、类型、几何、颜色及所有影响绘制的参数。不一致必须失败，不能复制主高亮来制造一致。
3. v3 继承并复用冻结 v2 的检查，不复制整套采集器或验证器。新来源绑定到冻结候选；新增状态字段必须由校验器验证。
4. 保留正式 TerrainLayer 独立生成、道具复制替换、12 个图像角色、同一次 frame_post_draw、完整 RGBA 相等、实例 ID/alpha 对应、实际 UI/单位排除和至少三可见实例门槛。
5. 运行六组合无窗口结构检查与针对本次缺陷的正反例。它们只证明结构，原生像素与布局由 Dot 验证；失败日志保留。
6. 新云端任务先取得 10×10/720p 的原图并验证全部像素前置。前置不成立时，保留原件并停止后续采集；已经成功建立像素前置后才继续其余五组各一次。不得重试同一冻结任务、修补运行材料或降低门槛。
7. 当前素材最低三可见实例和 T1–T6 仍是独立要求。旧图的第三根石柱零 ID 作为复测项保留；不能修改 fixture、改变镜头或删去分母来回避。

## 技术来源

Godot 的 [Viewport 文档](https://docs.godotengine.org/en/4.6/classes/class_viewport.html)说明 push_input 在指定 Viewport 内处理输入，并区分视口坐标与宿主坐标；本项目的子视口路由行为须由真实会话回归证明。[RenderingServer 文档](https://docs.godotengine.org/en/4.6/classes/class_renderingserver.html)说明 frame_post_draw 在全部 Viewport 更新结束后发出。上述 API 说明不能代替本项目的真实路由回归和原图验证。
