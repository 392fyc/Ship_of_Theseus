# UI 与战场美术自检

此流程用于本项目后续视觉候选的制作与交付。目标是让代理在交付前发现并修复可判断的缺陷，把需要用户介入的事项收敛到审美方向、玩法含义和最终认可。已批准内容以用户最新裁决为准。

## 当前交付与后续审查

2026-09-27，用户通过当前成果的人类审查并授权提交合并。交付包括九类地形拼接库、深浅水连续过渡、障碍变体、地图创作工作台、正式战斗试运行，以及仅支持正方形的 10—25 格边长设置。当前范围及证据见 [本次集成记录](release-2026-09-27.md)。

下一阶段是外部 Claude 对截至当前全部美术、UI/UX 和素材产线的独立审查。用户明确允许 Claude 调整、删减或推翻现有视觉及制作方案；需要重新制作素材时，由 Claude 提供材质或式样参考，交给 Codex 实施。审查入口见 [全量审查索引](../claude-review/README.md)。这些权限取代本范围内旧记录中要求保持视觉冻结的限制，玩法事实仍按设计库核对。

本流程提供可以复现、能拒绝已知错误的制作和验收入口：预期独立于绘制实现；素材、组合、整屏各有证据；深浅水有实际可见的连续过渡；多格代表水域与单格极端测试分别验证；正确样本通过且旧错误样本被同一检查拒绝；独立审查与限制如实记录。技术检查不等于所有地图构图、完整关卡或遭遇平衡已经验收。

## 素材生成与入库

1. 先写素材用途、实际显示尺度、透视、光照、透明边界、重复方式及禁止内容，并绑定已批准风格参考。只生成一个明确职责的部件；地表底材不包含岸沿、棋盘框、地形标签或建筑布局。
2. 完整记录参考摘要、原始提示、源图及文件摘要。提示写了“无缝”“无亮边”不构成检查结果。生成失败或视觉不合格的图保留为候选，不进入批准素材组。
3. 用引擎原生预览查看单张、3 × 3 重复和实用尺寸。逐项记录材质身份、烘焙高光／阴影、边缘接缝、周期性焦点、透明留白、细节密度。只查哈希不算视觉入库。
4. 素材只有在最小邻接例子中通过后才放入整屏。材质单体正常而组合错误时，用关闭岸沿、关闭底材、纯色替换等分层对照定位负责的层。
5. 确定缺陷位于 PNG 时，再按原参考和单一修正目标重新生成；缺陷位于数据或绘制时修该层，并重新采集其影响范围。原图不被无记录覆盖。

当前水与石材的原生入库预览入口是 `tests/capture_courtyard_material_intake.gd`。它核对来源摘要并输出单张、重复和实际尺寸图；输出中的 `pending_review` 必须由实际查看和记录补全，不能自动转为认可。

## 每轮执行顺序

1. **写清本轮验收句。** 每句都可对应画面中的位置或可复现状态。例如“浅水在棋盘边界继续延伸时宽度不突变”“头像四边贴合内框”“同一单位常态与悬停时使用同一头像框”。同时列出已定版内容及本轮范围。
2. **把关系画成最小样例。** 地形先列需要覆盖的相邻组合及端头、直线、转角、分叉；图标先列各技能的主体、动作方向与识别特征。存在设计依据缺口时先核查权威资料。
3. **先用简单形体验证结构，再上材质。** 检查河道和陆地连续、墙体与房间及门洞对应、路径可解释、前后遮挡合理。结构错误不以更多装饰掩盖。
4. **在实际引擎中采集固定状态。** 检查最终使用尺寸的全屏图；必要时再看局部。检查常态、交互状态与两种目标分辨率。涉及镜头、运动或遮挡恢复时采集实际连续帧。
5. **逐项寻找反例。** 沿所有水陆边、墙脚和画面边缘检查，不只看最醒目的中心。每项记录“通过／未通过／无法判断”、具体位置、图片和理由；有明确缺陷就继续修正。
6. **独立复核。** 对范围明确且存在视觉风险的变更，审查者先只看目标、已定版参考和实际图片，不接收实现者“已经修好”的解释。先给视觉问题，再用代码核实成因。同一主代理已知问题的复看不能称为盲测。
7. **只展示已自检的候选。** 修复后重录受影响画面，并检查相邻对象和整屏回归。功能测试、视觉检查、用户认可分别记录。清楚说明已修内容、剩余不确定项和实际下一步。

## 进入整屏检查前必须满足的条件

- **规格先于预览。** `water-visual-contract.json` 单独规定样例中心、周边类型及图像标准。检查不能用待测函数的输出产生自己的正确答案。中心深水、外圈浅水是本次深度展示样例的要求，不是对所有地图新增地形规则。
- **数据与画面分别检查。** 数据正确但把深水画成浅水也必须被拒绝；正确的绘制不能替错误的地图含义背书。语义图、材质图与最终图使用同一份场景数据。
- **关系本身需要证据。** “中心是深水”和“深浅颜色有区别”均不能证明过渡成立。用穿越边界的多点颜色曲线检查中间色宽度、突跳与反向变化，再看多格水域的实际材质图。单格极端样例只用于校准，不能替代代表性水域展示。
- **过渡需要共用坐标。** 深浅水在共享连续坐标中混合，场内外及转角使用同一规则；不能在各条格边独立叠加窄色带，造成接缝和角部色块。
- **检查器先过错误对照。** 石岸实色亮带、中央浅水、深水使用浅水颜色是已知反例。正确样本通过、反例被拒绝才算该项检查有效；不允许以坏样本标签直接返回失败。遗漏反例时暂停该项通过结论，修检查或转为无法自动判断。
- **局部缺陷用局部证据。** 岸线沿各边分别采样，水深按同位置、同材质坐标比较；不能以整屏平均误差稀释细线或单格错误。阈值、采样区域和限制存入规格，改阈值需说明依据并重新校准正确与错误样本。
- **稳定采集才可比较。** 整屏固定种子和动画时间，连续两帧必须完全一致；源代码或素材采集中变化即拒绝该批证据。静态冻结检查不替代独立的动态与交互检查。
- **基线需有用户认可依据。** 当前地形批准记录为 `assets/prototype/battlefield_courtyard/terrain-kit-approved.json`，水深另有 `water-depth-approved.json`；尺寸和功能的最新整屏证据为 `reviews/2026-09-27/terrain-map-size-v1/archive-manifest.json`。标为 `candidate_unapproved` 的历史截图仍是当时的候选记录，不自动扩展批准范围。后续 Claude 可以修订视觉基线，但必须记录新来源、重跑受影响检查，并保留旧证据的历史身份。

执行 `tests/test_courtyard_water_visual_contract.gd` 得到实际像素检查、语义检查及坏样本校准结果。成功只说明它覆盖的具体错误被拦截，不能推出所有水岸、全部缩放或所有自然度问题均正确。

### 顺序执行入口

```powershell
./tests/run_courtyard_visual_validation.ps1 -GodotPath <godot-executable> -OutputDirectory <new-absolute-directory>
```

入口依次运行水岸与端点色调、水深连续性、邻接、素材、整屏、交互。连续性步骤必须输出代表水域与曲线对照，并拒绝硬切和旧窄色带。每步核验明确的结果字段、必要产物及已记录的图片摘要；缺字段、缺图、反例未拦截或进程失败即停止，不继续产生“整批通过”。每批使用全新仓库外目录。结束状态是 `automated_evidence_complete_review_pending`，随后仍须实际看图、独立复核与用户视觉认可。

## 必查内容

| 范围 | 检查方法 | 不通过的例子 |
| --- | --- | --- |
| 地形身份 | 对照正式类型；隐藏说明后检查形体、材质和深浅层次 | 只有不同颜色的同一种石砖；把装饰名称写成正式规则类型 |
| 地形邻接 | 检查同类连续、异类过渡、边缘与转角；更换邻地后再看实际画面 | 河宽突然改变、岸线穿入陆地、两岸重复描边、墙体连接留缝 |
| 水岸自然度 | 同时检查局部样例与整条河道；湿土靠材质过渡，石岸靠石面及临水暗面形成厚度 | 连续等宽亮线围住水面；土岸和石岸都像镶边地板；浅深水之间出现岸沿 |
| 场景组织 | 查看完整建筑地面、墙体、门洞与道路关系，沿边缘检查场外延伸 | 墙随机落在通路中央；装饰与场内没有空间联系 |
| 头像与图标 | 先看最终使用尺寸，再看同源细节；核对透明区域和容器边界 | 无头像、内框留白、脸部高光吞掉结构、图标仍为占位 |
| 文字与状态 | 读出关键数字；检查中文、溢出、前景对比和状态一致性 | 乱码、数值难辨、悬停换框、前景遮住单位标签 |
| 技能含义 | 不看名称描述主体和动作，再和已批准语义对应 | 四个技能全像同一种挥砍；长剑缩小后像匕首 |
| 风格一致性 | 将候选和已批准原画并列检查色域、材质、笔触、明暗和细节密度 | 符号精细度、光效或写实程度与人物原画明显脱节 |
| 动态与交互 | 实际移动、缩放、悬停、退出遮挡、切图 | 静态图正常但移动后穿插、切图残留、淡化不恢复 |

头像留白、形状对称性、资源引用、地图边界坐标等可量化问题，应结合几何或文件检查；自然度、动作语义、构图和材质质感仍须实际看图。测试只证明它覆盖的条件。

## 棋盘邻接的覆盖范围

当前拼接库覆盖九种正式地形，检查 32 种合法异类接壤、同类连续、内外角、窄道、斜接、三四种地形交会、墙端及分叉、场内外连接。四种排除组合包含对角接触。组合清单和工作台说明见 `terrain-kit.md`，统一运行入口是 `tests/run_terrain_kit_validation.ps1`。固定样例不能证明任意地图构图与全部美术语义都正确。

Godot 的 Terrain Sets 使用边和角匹配邻地选择变体，这为组合清单提供了实现依据；当前项目使用现有 Grid 与绘制层实现同类原则，并未迁移为 TileMapLayer。[Godot 4.6 文档](https://docs.godotengine.org/en/4.6/tutorials/2d/using_tilesets.html#creating-terrain-sets-autotiling)

## 证据一致性

- 每一批图片记录场景、角色、窗口尺寸、显示状态、帧号、文件摘要和相关源码摘要；同一目录内不混入未标识的旧版本。
- 检查实际整屏尺寸。局部图如有使用，应记录对应原始帧与区域，不能拿另一次运行的局部当作该整屏的细节。
- 截图之后继续改动了影响画面的代码或素材，受影响截图即需更新。
- 保留原始运行输出；“已采集”与“已查看”分别记录。截图数量不能代替逐项结论。
- 当前战场统一采集入口：`tests/capture_courtyard_visual_review.gd`。邻接对照与变更检查：`tests/test_courtyard_terrain_adjacency.gd`。

## 漏项的关闭条件

每次用户或代理发现漏项，在 `reviews/` 保存：原始预期、实际反例、产生错误的层、未拦住它的检查、负责修正者、受影响范围、修正证据、同一检查拒绝反例的结果和剩余限制。当前流程与回执只保留有效结论，旧结论放入历史记录。

出现同类复发时，先判断检查是否没有运行、没有覆盖、预期错误或判定能力不足，再改相应环节。只有修正落地并重跑证据后，才把该行动项记为完成。独立视觉审查仍可帮助发现未知问题，但一次未发现问题不能抵消客观反例；审查者也需要先说明它能识别哪些已知错误。

## 自主迭代和用户介入

代理自行处理能够定位的接缝、错位、遗漏、遮挡、状态不一致和已明确规格的偏离；同类问题反复出现时先修共用规则，再复查受影响场景。方法不确定时查维护方文档或开发者制作资料，并把采用的方法落实到可观察样例。

在答复中已经认定某处存在明确缺陷时，继续完成修正、实际采集与复核，不以解释缺陷作为该轮终点。只有用户明确限定为解释、要求暂停，或修正确实涉及尚未授权的新裁决时，才停在说明或提问。

当画面可辨但有两种都合理的审美方向、技能含义缺少裁决，或修正会改动已定版风格／玩法时，才提出带实际对照的集中问题。不能因一次检查“未发现问题”就声称画面没有缺陷。

流程成效通过后续实际记录衡量：代理在交付前发现的具体问题、用户又指出的漏项、同类问题是否再次出现。样本不足时不报虚假的识别率或宣称已能独立完成全部美术判断。
