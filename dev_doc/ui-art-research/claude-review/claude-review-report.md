## 0. 结论摘要

当前成果是一个功能完整、地形与 HUD 已有成品感的战斗原型。但它还不是一套视觉统一的游戏画面，而且产线存在会持续放过同类缺陷的系统性缺口。

最重要的六项：

1. **缩小采样没有任何策略（P0，产线）。** 按代码推算的场景真实尺寸：

   - 试战中的森林树缩小约 16.5 倍，残墙碎石约 41.6 倍。
   - 庭院入口约 6.4 倍，默认战斗中的剑圣棋子约 6.4 倍。
   - 纹章约 11 倍，头像约 9 倍。
   - 墙顶每个屏幕像素采样约 10 个纹素，墙面约 22 个（镜头 1.0）。
   - 连续地表与水面在纵向约 7 个（10×10 试战约 7.5 个）。

   这些素材全部没有 mipmap，也没有按显示尺寸制作的母版。与面积滤波参考相比，平均色差 ΔE76 为 3.1–13.6；缩放变化 2% 时，画面抖动是参考的 1.5–4.5 倍。模拟显示，开启 mipmap 并加 −0.5 的偏置后，20 个场景档位全部达到"ΔE76 ≤ 4、抖动 ≤ 参考 × 1.3"（§3.1）。

   相关导入设置大多没有进入版本库：`.gitignore:3` 忽略全部 `*.import`，只放行庭院目录。所以只在本机改导入参数，改动进不了发布包（P-01）。

2. **验收证据不代表实际运行配置（P0，产线）。** 有两处不一致：

   - **拉伸**：21 个采集与测试脚本关闭了 `canvas_items` 拉伸。在 1920×1080 下，HUD 底栏与实际一致，但 `Turn Order`、调试提示、战场与剑气数字都与实际不同（e03 对 e04）。
   - **渲染器**：所有验证都用 Compatibility 渲染器，而发行版按项目默认使用 Forward+。

3. **同一画面里成品和占位混杂（P1）。**

   - 正式试战中全部单位仍是文字方块。
   - 默认战斗和 RunScene 战斗仍走亮绿占位地图。
   - 右上角是英文开发面板。

   玩家实际看到的画面由占位元素主导。

4. **美术方向的权威记录与已批准成果互相矛盾（P1，需裁决 D-1）。** KB 现行裁决要求"统一的略微精细像素化系统、UI 与像素边框用 nearest"。已批准成果却是：

   - HUD 是平滑矢量框体；
   - 技能图标、头像、纹章的生成提示词写明 `no pixel art` 或 `painterly`；
   - HUD、头像与棋子用 Linear，地形道具、墙与水面用 Nearest，地表着色器用无 mipmap 的 Linear。KB 允许精细人物用 Linear（第 81 行）、要求地形用 nearest（第 91 行），但 HUD 与 UI 边框用 Linear 与 KB 的"UI nearest"不一致。

5. **技能图标在 52 像素下的语义和制作都有缺陷（P1）。**

   - 五枚中四枚 alpha 羽化、整体半透明。
   - 主色调挤在 11.7° 的色相窄带内。
   - 盲测中"一闪"无法独立辨认，"居合"只有中等把握。

6. **玩家可见文本暴露开发信息（P1）。** 备战、事件结果等界面直接显示内部 ID 和 `[占位]`、`[提案]` 等开发备注。

## 3. 关键证据说明

### 3.1 缩小采样量化（V-07、V-10、V-20、V-28，CR-01）

**方法。**

- 显示高度按代码推算：
  - 庭院镜头 1.36（`battlefield_courtyard.gd:222`）
  - 试战镜头：10×10 为 0.92，25×25 为 0.418（`terrain_battle_session.gd:99-106`）
  - 默认战斗镜头 1.0
  - 试战设置了 `transition_preview`，跳过环境道具（`courtyard_board_view.gd:530-531`），只剩棋盘内的森林树（缩放 0.91–1.02，`:513`）和残墙端的碎石（缩放 0.35，`:521`）
- 采样：用与引擎一致的方式缩小源区域（nearest，或无 mipmap 的双线性），与面积滤波结果比较；再把缩放增加 2%，比较前后两档的差异，用来近似镜头缩放时的闪烁。
- 修正后的对照：同一脚本另算两种"开启 mipmap"的模式——`mip`（2×2 预乘 alpha 盒式 mip 链加三线性采样，偏置 0）与 `mip:-0.5`（偏置 −0.5，只在 Forward+ 下可实现）。
- 验收目标（CR-01）：ΔE76 ≤ 4；抖动 ≤ 参考抖动的 1.3 倍。抖动判据只在缩小倍数 ≥ 1.5、输出 ≥ 20 像素、参考抖动 ≥ 0.5 时适用；不适用的行只看 ΔE。
- 复现：`tests/claude_review/sampling_sim.py`；20 行完整数值在 `evidence-2026-09-28/sampling-sim.json`。

| 素材与场景（720p） | 显示高 | 缩小倍数 | 过滤 | ΔE76 当前 / mip / mip−0.5 | 抖动 当前 / mip / mip−0.5（参考，取当前模式的参考值） |
| --- | --- | --- | --- | --- | --- |
| 森林树 · 试战 10×10 | 57.7 | 16.5 | nearest | 7.79 / 2.64 / 2.20 | 8.91 / 2.80 / 2.80（3.18） |
| 森林树 · 试战 25×25 | 26.2 | 36.2 | nearest | 8.32 / 2.67 / 1.97 | 10.14 / 1.43 / 1.92（2.29） |
| 森林树 · 庭院树丛 | 166.3 | 5.7 | nearest | 4.77 / 2.81 / 1.69 | 5.19 / 1.67 / 2.32（2.67） |
| 碎石 · 试战 10×10 | 11.9 | 41.6 | nearest | 9.04 / 3.56 / 2.52 | 不适用 |
| 碎石 · 试战 25×25 | 5.4 | 91.6 | nearest | 9.67 / **5.11** / 3.67 | 不适用 |
| 入口 · 庭院 | 116.7 | 6.4 | nearest | 6.72 / 2.85 / 1.77 | 5.73 / 1.39 / 1.99（2.13） |
| 剑圣棋子 · 默认战斗 | 80.0 | 6.4 | linear | 9.15 / **4.44** / 2.87 | 5.74 / 1.92 / 2.58（2.96） |
| 剑圣棋子规格 · 试战 25×25 | 33.4 | 15.3 | linear | 13.57 / **4.22** / 2.39 | 8.88 / 1.86 / 2.33（2.60） |

- ΔE76 约 2.3 就是人眼可察觉的差异。
- **可达成性**：`mip:-0.5` 在全部 20 行（720p 与 1440p）都达标；偏置 0 的 `mip` 达标 14 行，未达标的 6 行是 5 行剑圣棋子（ΔE 4.2–4.8）和 25×25 试战中的碎石。所以在 Compatibility 下（偏置恒为 0），棋子与碎石必须另做接近显示尺寸的母版，只开 mipmap 不够。
- 碎石几行的抖动不适用：输出只有几像素，缩放 2% 后整数尺寸不变，比值无意义，`sampling-sim.json` 中记为 `null`。
- 2560×1440 下倍数减半，但除庭院树丛（2.9）外仍全部大于 3。
- 墙面与材质不在此表：它们是按世界坐标铺贴的 UV（`courtyard_board_view.gd:772` 每世界单位 10 纹素，`:776` 每单位 22.36 纹素），缩小比例见 CR-01 位置表。

视觉上的取舍（e15）：当前采样更"脆"，但高光碎成散点；面积滤波稳定，但偏软。所以 CR-01 要求在引擎内并排比较后由用户选定。

依据：Godot 官方导入文档说明，2D 中因镜头或 CanvasItem 缩放缩小时，mipmap 可避免颗粒感；CanvasItem 文档说明，`LINEAR` 和 `NEAREST` 远看会有颗粒感，原因是没有采样 mipmap。

### 3.2 采集配置与实际运行（P-03、P-15，CR-02、D-5）

**拉伸。** 21 个脚本设置了 `root.content_scale_mode = CONTENT_SCALE_MODE_DISABLED`：`tests/` 下 19 个，`dev_doc/.../hud-myrmidon-portrait/capture_review.gd:15` 与 `myrmidon-skill-icons/capture_candidate.gd:15` 两个。

我用 `tests/claude_review/capture_scene_native.gd` 在同一提交上做对照：

- **保留项目拉伸**：1920×1080 时逻辑视口仍是 1280×720，由引擎统一放大 1.5 倍（e04）。
- **关闭拉伸**：逻辑视口变成 1920×1080，HUD 靠自己的缩放系数放大。
  - 底栏区域与保留拉伸时基本一致：y ≥ 890 的范围内只有 2 个像素相差 1 级。
  - 剑气数字"0"区域有 787 个像素不同，最大差 188。
  - `Turn Order`、调试提示与战场没有缩放，面板漂到屏幕中部（e03）。

结论：既有 1920 证据只对 HUD 底栏有效。

**渲染器。**

- `project.godot:20` 声明 `Forward Plus`，也没有渲染方式覆盖，所以默认是 `forward_plus`。发行构建 `scripts/codex/build-windows-release.ps1` 导出时没有指定渲染器。
- 所有验证采集（Codex 的与我的）都用 `--rendering-method gl_compatibility`。

我补拍了两组对照：

- **默认战斗（无动画）**：两种渲染器下只有 0.11% 的像素差值超过 8；HUD 区没有差值超过 8 的像素，只有 1–2 级的小差。
- **庭院场景**：5.7% 的像素差值超过 8，平均亮度（RGB 三通道均值）46.1 对 46.3（e33）。这个场景有风动和涟漪动画，而我的通用采集没有固定动画时间，所以这部分差异**不能归因于渲染器**。

另外，官方文档说明 `texture_mipmap_bias` 在 Compatibility 下恒按 0 处理。所以 CR-01 方案 A 的偏置实验必须用发行渲染器采集。
