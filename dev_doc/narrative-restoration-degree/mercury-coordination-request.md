## 一 · 背景

Plan-1 的世界观量级与实际战斗量级之间原先存在落差：叙事里写着宇宙级的存在，玩家在战斗里遇到的却是人间尺度的对手。用户裁决的解法是在设定内加一层解释，称为**世界之理的复原度**，简称**理**。

这层解释的要点，与机制相关的只有三条：

1. 每个敌人都是原初世界某位存在投影进某片小世界的一个**投影实例**。内在是本体，所以复原出来的是它本身的能力；实例是投影，所以理未回全处它的能力残着一部分。理尚浅时的那副样子称**未复原之姿**。
2. 理越复原，敌人越趋近它在原初世界里本来的样子。宇宙级的那副样子记的是原初世界当初的记录，理始终留着一点回不去，所以那个样子**始终在够不到的地方**。
3. 描述一位敌人「是谁」属于本体的事，各难度下**描述文本完全相同**；随难度变化的只有**属性数值与技能特性的开放范围**。

叙事侧在此基础上给出了成形的难度设计（下节详述），并且注意到 `run-loop.md` 早已为此留好接口。**叙事侧提供的是填这个接口的设计意图与命名，不要求新增任何一条轴。** 机制归属完全不变：难度系统的结构、参数、曲线、实装全部属于 Mercury 线。

### 叙事侧的难度设计 · 已定

用户 2026-07-29 裁决 [已定]：

- 一共四档。前三档是寻常难度分级——**简单 / 普通 / 困难**——**不计理**。
- 第四档叫**旧日重现**。从这一档开始交出「理」这条量：玩家自己逐条叠加可选项，每加一条，船就多担一分修复的工作，理便多还回来一分。
- 这条量在界面上就叫**理**，以百分比计，从 0 起，**可以突破 100**。
- 叙事上，玩家叠加＝船主动把理拉回来更多，而修复世界之理本就是船存在的意义。代价与它是同一件事：世界越接近本来的样子，对面也越接近本来的样子。

**关于百分比与突破 100 的性质说明**：这是叙事侧对**呈现方式**的说明——玩家看到的读数长什么样、从哪里起算、能不能越过 100。它不是对**曲线形状**的要求。理这条读数与敌方数值之间怎么换算、每条可选项各值多少、曲线是线性还是别的形状、有没有上界，全部属于 Mercury 的调参空间，本方不提任何数值、不提任何曲线。

## 二 · 与机制现状的逐条核对

### 2.1 旧日重现的可叠加设计 与 现有的开局难度档留位

**现状实查**：

- `run-loop.md:255`：「**难度两轴（2026-07-02）**：本表是**幕数递进轴**；另有**开局难度档**（类 Hades 热度，系统细节后置、v1 固定基础难度留接口）。热度奖励设计须守 meta 横向红线（不给纵向战力）。」
- `run-loop.md:393-394`：`RunConfig` 结构里 `difficulty: String  # 开局难度档（热度，系统后置；v0 = "base"）`。
- `run-loop.md:11`：v0 实装记录明确列出「**v0 未做**：……二三幕 + 幕 Boss 独有机制 + **热度系统**」。

**结论**：接口在 `run-loop.md:255` 已经写好并留位，数据结构位在 `run-loop.md:394` 已经占好，系统本身尚未实装。**旧日重现这套可叠加设计填的正是这个留位，不是新开一条轴。** 前三档简单 / 普通 / 困难同样落在这个留位上，只是这三档不交出「理」这条读数。

**现有的难度两轴表述要怎么说才不冲突**：叙事上，理由玩家在启程前拨定，一轮航程之内始终是那个刻度；航程之内逐幕加压是这一轮航程自身的进程，玩家在途中并不拨动它。这与机制现状恰好吻合——`run-loop.md:150` 已经写明恢复量「**不随幕变动、只随开局难度档变动**，run 内恒定」。

建议 `run-loop.md:255` 的两轴表述补一句可直接采用的措辞：

> 两条轴的性质不同：**开局难度档**由玩家在启程前一次性拨定，一轮之内恒定；**幕数递进轴**是一轮航程自身的进程，一轮之内自动展开。玩家能主动拨动的只有前者。

**吻合度**：接口层面完全吻合，本条无需机制让步。

### 2.2 敌人属性随难度提升 现在挂在哪条轴上

这一条是本次核对**最大的一处不吻合**，已重新实查确认。

**现状实查**：

- `run-loop.md:243-249` 的难度缩放表只有 `Act 1 / Act 2 / Act 3` 三列，没有开局难度档这一维：
  - `run-loop.md:245`：`Enemy HP | x1.0 | x1.5 | x2.0`
  - `run-loop.md:246`：`Enemy Attack | x1.0 | x1.3 | x1.6`
  - `run-loop.md:247`：`Wave Count | 1-2 | 2-3 | 2-3`
  - `run-loop.md:248`：`敌人阶梯组合与词条数量 | 区间下限 | 中段 | 区间上限`
- `run-loop.md:155` 把归属写死了：「磨损逻辑（两轴解耦）：恢复**不满额** + HP 跨关继承 → 精英房血量代价跨关发酵；**幕间压力全部交给敌方成长轴（倍率+词条数），恢复压力交给玩家自选难度档**。」
- `run-loop.md:153` 佐证同一口径：恢复量「更高热度档更低（**热度系统第一个具体旋钮**，曲线 [占位]）」。
- `run-loop.md:395-396`：`RunConfig` 里挂在 `difficulty` 旁边的只有 `recovery: { percent_max_hp, declinable }` 一项。

**结论**：开局难度档目前承载的实质旋钮**只有恢复量**一项，敌方属性倍率完整地挂在幕数递进轴上，`run-loop.md:155` 还明文把两者解耦、把敌方成长整块划归幕数轴。

叙事侧的「旧日重现」要求的正是这条被划走的东西：玩家每叠一条可选项，理多还一分，**敌人的属性数值向它本来的样子多趋近一分**。这需要开局难度档上出现一条作用于敌方属性的承载，并需要 `run-loop.md:155` 的两轴解耦表述随之修订——修订后的口径大致是「幕间压力来自幕数递进轴；开局难度档同时作用于恢复压力与敌方能力的开放程度」。

**可用的既有落点**：`enemy-and-ai.md:175` 记录 v0 词条引擎实装时，`data/waves/` 的敌人条目已带 `stat_scale` 字段，`damage_calculator.gd` 已有 affix 乘区。这说明敌方数值缩放的挂载点在代码层已经存在，缺的是把开局难度档这条输入接进去，以及在文档层承认这个归属。具体怎么接由 Mercury 定。

### 2.3 某些程度以上解锁额外的特性或技能 能否由现有词条制承载

需要分成两半看，一半现成，一半需要新东西。

**特性一半 · 词条制可承载**：

- `enemy-and-ai.md:161`：「**实现口径**：词条=**类似人物被动的技能**——不走 buff/debuff 结构……需要敌方单位的**被动技能挂载点**……词条以 JSON 声明式定义（`data/affixes/`），normal 层恒为空。」
- `enemy-and-ai.md:175`：被动挂载点已按方案 A 实装（`unit.gd` 的 `apply_affixes` + `tactical_manager.gd` 的 `_apply_affixes` 时机分发器），v0 池 5 基础 + 2 特殊。
- `enemy-and-ai.md:156`：「**词条数量在区间内按难度两轴取值**：开局难度档（系统后置）× 幕数递进」。

结论：「理到某个程度以上，这位存在多显出一分本来的手段」这件事，用现有词条制表达是顺的——追加词条即可，机制上已有声明式定义与运行时注入两端。而且 `enemy-and-ai.md:156` 已经把词条数量写成两轴共同取值，开局难度档在词条数量上**名义承载已经存在**，与 2.2 的属性倍率情况不同。

**技能一半 · 需要新的表达**：

- `enemy-and-ai.md:127`：敌人模板的 `"skills": ["slash"]` 是一个固定数组，没有条件追加的表达。

结论：如果叙事上要在某个复原程度以上让敌人开出一个**主动技能**（而不只是被动词条），现有模板结构缺一个「按难度阈值追加技能」的字段或规则。这属于新增，是否值得做由 Mercury 判断——叙事侧对「特性」与「技能」两种表达都接受，只要「越复原越多显出本来的手段」这件事能被表达出来即可。

**一处顺带发现的口径张力**：`enemy-and-ai.md:156` 说词条数量按「开局难度档 × 幕数递进」两轴取值，而 `run-loop.md:248` 把词条数量放进了纯 Act 表、`run-loop.md:155` 又说词条数一并属于敌方成长轴。两处口径略有出入，与本请求方向一致但先于本请求存在。本方仅报告，处理与否由 Mercury 定。

### 2.4 各难度下描述文本相同 只有属性与技能开放不同 对敌人数据结构意味着什么

**现状实查**：

- `enemy-and-ai.md:117-135` 的敌人模板示例，字段为 `id` / `name` / `base_stats` / `growth_rates` / `skills` / `ai_behavior` / `target_priority` / `exp_reward` / `drop_table`。其中：
  - `enemy-and-ai.md:119`：`"name": "Goblin Warrior"` —— 叙事可用的文本字段目前**只有一个名字**，没有描述或背景文本字段。
  - `enemy-and-ai.md:120-125`：`base_stats` 是单一的一组常量。
  - `enemy-and-ai.md:127`：`skills` 是单一的一个固定数组。
- `enemy-and-ai.md:169-173` 与 `run-loop.md:444-448` 的 `EnemyTemplate` 扩展字段为 `tier` / `base_affixes` / `special_affix`，同样没有叙事文本字段。

**结论**：这条设定对数据结构的要求是一句话——**叙事文本层与数值开放层要能各自独立地随难度取值**：

- 叙事文本层（这位是谁）：全难度共用一份，随难度恒定。现有结构缺一个存放位，需要新增一个描述或文本引用字段。
- 数值开放层（这位现在复原到哪一步）：随难度取值。`base_stats` 与 `skills` 需要有一个不改写模板原始值的覆写或乘区表达；`base_stats` 侧 `stat_scale`（`enemy-and-ai.md:175`）已有先例，`skills` 侧见 2.3 后半。

好处是这两层一旦分开，一位存在只需要写一份叙事文本，其在各难度下的样子由同一份模板派生，叙事侧的维护量不随难度档数增长。

### 2.5 宇宙级 apex 够不到 与 敌人五层分级的关系

**现状实查**：

- `enemy-and-ai.md:148-154` 的五层阶梯表：`Normal` / `Lesser Elite` / `Greater Elite` / `Elite Chief` / `Act Boss`，其中 `enemy-and-ai.md:154` 的 Act Boss 词条数记为「随难度」。
- `run-loop.md:445`：`tier` 枚举与上表一致。
- `enemy-and-ai.md:181`：Act Boss 是传奇层级敌人，词条数量随难度递增，且每个 Boss 有独有机制系统。

**结论**：两者是正交的两件事，**五层分级完全不动，不需要新增任何东西**：

- **tier 说的是编制位置**——这位在这场战斗里是杂兵、精英、头目还是幕 Boss。
- **理说的是复原程度**——同一位存在从未复原之姿一路趋近它本来的样子。

宇宙级的那副样子是这条趋近的渐近上界，理始终留着一点回不去，所以它**永远落在开放范围之外**。既然够不到，它就不需要在数据结构里占一个位置：它是叙事文本里被记述的样子，不是任何一档难度下会被生成出来的敌人。因此本方**不请求**新增第六层 tier，也不请求在 tier 枚举上加任何值。

顺带一提，`enemy-and-ai.md:154` 现有的「Act Boss 词条数随难度」写法与理这条量天然契合，可直接沿用。

## 三 · 需要 Mercury 配合的事项

按优先级排列。每条写明叙事侧的需求、为什么需要、建议落点、以及本方的边界。

### P0-1 · 开局难度档上需要一条作用于敌方能力的承载

- **叙事侧需求**：玩家每叠一条可选项，理多还一分，敌人的属性数值向它本来的样子多趋近一分。这是「旧日重现」这一档能成立的最低要求。
- **为什么需要**：`run-loop.md:155` 现把敌方成长整块划归幕数递进轴，开局难度档只承载恢复量（`run-loop.md:153` 称之为热度系统第一个具体旋钮）；`run-loop.md:243-249` 的难度缩放表也没有开局难度档这一维。不补这条承载，理这条量在机制上落不到敌人身上。
- **建议落点**：`run-loop.md` 的「难度缩放」一节——`run-loop.md:243-249` 表旁增设开局难度档的作用说明，并修订 `run-loop.md:155` 的两轴解耦表述。代码层的挂载点可考虑复用 `enemy-and-ai.md:175` 记录的 `stat_scale` 与 damage_calculator 乘区。
- **本方边界**：本方不提乘区数值、不提曲线形状、不提每条可选项各值多少、不提上界，也不指定挂在哪个乘区上。这些全部由 Mercury 定。

### P0-2 · RunConfig 的 difficulty 需要能表达档位加可叠加可选项

- **叙事侧需求**：前三档是单选的寻常分级；第四档「旧日重现」之下，玩家逐条叠加可选项，叠加结果派生出一个供玩家阅读的读数——界面上就叫**理**，以百分比计，从 0 起，可以突破 100。
- **为什么需要**：`run-loop.md:394` 现在的 `difficulty: String` 是单值，表达得了四选一，表达不了「第四档 + 一组已勾选的可选项」。
- **建议落点**：`run-loop.md` 数据结构一节的 `RunConfig`（`run-loop.md:393-396`）。结构形态由 Mercury 定，叙事侧只要求两件事能被表达：一是哪些可选项被勾选，二是由此派生出一个可显示的读数。
- **本方边界**：本方不请求规定可选项的条目内容、条数、互斥关系、解锁条件，也不规定读数的换算方式。百分比与突破 100 是**呈现方式**的说明，不是曲线要求——这个区别很重要，`run-loop.md:255` 那条留位注记里的「系统细节后置」仍然完整有效。

### P1-1 · 敌人模板需要一个随难度恒定的叙事文本字段

- **叙事侧需求**：一位存在在各难度下的描述文本完全相同，因为描述说的是「这位是谁」，属本体的事。
- **为什么需要**：`enemy-and-ai.md:117-135` 的模板目前叙事可用的只有 `enemy-and-ai.md:119` 那个 `name`，没有描述文本的存放位。叙事侧写好的敌人文本现在无处安放。
- **建议落点**：`enemy-and-ai.md` 的「敌人模板」一节，模板示例与 `enemy-and-ai.md:169-173` 的 Schema 扩展块。字段名与形态由 Mercury 定，可以是内嵌文本也可以是指向叙事资源的引用键。
- **本方边界**：本方提供文本内容与一份存放位的需求，不指定字段名、不指定本地化方案、不请求把叙事文本正文写进机制文档。

### P1-2 · 数值与技能的难度开放需要与模板原始值分离

- **叙事侧需求**：随难度变化的只有属性数值与技能特性的开放范围，同一位存在始终是同一位存在。
- **为什么需要**：`enemy-and-ai.md:120-125` 的 `base_stats` 与 `enemy-and-ai.md:127` 的 `skills` 都是单一常量，没有按难度取值的表达。若靠复制模板来做多难度版本，同一位存在会分裂成多份，与 P1-1 的「描述文本相同」直接打架。
- **建议落点**：同 P1-1 的 Schema 扩展块。属性侧可沿 `enemy-and-ai.md:175` 的 `stat_scale` 思路推广；技能侧见下一条。
- **本方边界**：本方不指定覆写机制的形态，也不指定哪些属性参与开放。

### P1-3 · 某个复原程度以上多显出一分本来的手段 需要一条表达路径

- **叙事侧需求**：理到一定程度，这位存在会显出它本来就有、此前残着的手段。
- **为什么需要**：被动一半现成——`enemy-and-ai.md:161` 的词条制口径与 `enemy-and-ai.md:175` 的实装挂载点已可承载，`enemy-and-ai.md:156` 甚至已经把词条数量写成开局难度档与幕数递进两轴共同取值。主动技能一半缺表达——`enemy-and-ai.md:127` 的 `skills` 是固定数组，没有按难度阈值追加的规则。
- **建议落点**：`enemy-and-ai.md` 的「敌人层级与词条系统」一节。若 Mercury 判断全部走词条制即可、不新增主动技能通路，叙事侧接受——只要「越复原越多显出本来的手段」这件事能被表达出来。
- **本方边界**：本方不指定走词条还是走技能，不指定阈值位置，不指定池规模。

### P2-1 · 两轴性质的表述建议

- **叙事侧需求**：叙事上，理由玩家在启程前拨定、一轮之内恒定；一轮之内逐幕加压是这一轮航程自身的进程。希望机制表述与此同调。
- **为什么需要**：`run-loop.md:255` 现在的两轴表述只说了「本表是幕数递进轴、另有开局难度档」，没有点明哪一条是玩家拨动的。补上之后，叙事解释与机制口径可以逐字对上。
- **建议落点**：`run-loop.md:255` 那条注记。可直接采用的措辞见本文 2.1 节末尾。
- **本方边界**：这是措辞建议，采用与否由 Mercury 定，不影响任何行为。

- **叙事侧需求**：无。这是核对过程中顺带发现的既存口径出入，报告以供 Mercury 处置。
